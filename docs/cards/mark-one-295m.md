# Mark One 295M

My largest Mark One language model, 295 million parameters, trained at home on a general text mix and then on code.

| | |
|---|---|
| Project | Mark One |
| Dates | 200,000 training steps done on 27 Jul 2026; most tests here 1 to 8 Aug 2026; trained on to step 668,150 by 12 Aug 2026 |
| Size | 295 million parameters (294.7 million) |
| Hardware | Trained on one RTX 5090. The coding tests and the 512-window check ran on CPU. |
| Status | Paused, with the rest of Mark One |

## What it was for

I wanted to see how far a small model trained at home could get, on general text and on writing short Python programs that run and print the right answer. I measured it against Qwen's code models and against Python task suites of my own.

## What it was trained and tested on

- **General text.** A 29.1 GB mix of Stack Exchange, arXiv papers, Wikimedia, Project Gutenberg books, US government publications and generated logic problems, with part of each batch coming from a separate small set of generated practice problems. By 200,000 steps it had read about 1.23 GB, 4.17 bytes per parameter, about 4 percent of the mix. A compute-matched run would read about 60 to 80 bytes per parameter (a reference value), so the model is far under-trained and its results should be read that way.
- **Code, later.** A 6.63 MB set, three quarters source code and one quarter programs that had each been run and checked (32,000 of them), and later a much larger set of source code and checked programs.
- **How the tests were kept apart.** The 200-task suite was made by a seeded generator, frozen on 1 Aug 2026 and kept out of all training text by a substring check. The 775-task suite had 0 tasks present in any training corpus. The held-out windows come from the 900 MB held-out part of the training mix. The windows used against Qwen2.5-Coder-0.5B are held-out code, but that holdout is not proven clean.

## Results

Lower bits per byte is better.

- **My 200-task Python suite.** Each task gives the start of a short program, the model writes the end, and the answer is judged by running the finished program and comparing what it prints with the expected output. An earlier checkpoint solved 120 with 8 tries each. After one pass over the 6.63 MB set it solved 160, after five more passes over the same set 158, and after 20,000 further steps on the larger set 164. With one greedy try (its most likely answer) the counts were 107, 146, 149 and 150. At 164, five of the eight task families were 25 of 25; the weak ones were tasks needing the value a name holds (11 of 25), conditional expressions (10 of 25) and nested calls (18 of 25), by my recount of the rows. Limit: these are very small completions, not a public coding benchmark, and I scored no other model on them. The judge looks at printed output and nothing else, so an answer that reaches the right output by a shortcut also passes: in a 6-task check, one passing answer added a fixed number where it should have added a second variable. Five more passes over the same set did not help (158 against 160).
- **A larger suite, and a training mix that made it worse.** From the same starting checkpoint I trained 10,000 more steps on a mix of source code and checked programs of several kinds, and 10,000 on a mix whose checked programs were almost all inline arithmetic and conditional expressions (3.42 million generated transcripts). On a fixed suite of 775 Python tasks with one greedy try, the wider mix took the score from 550 to 565 (20 tasks gained, 5 lost, by my recount of the per-task rows) and the narrow mix took it down to 526 (11 gained, 35 lost). Every prediction I had registered for the narrow mix was wrong. Limit: one run per mix, and the suite is generated by my own scripts. I stopped building data for this skill after the narrow mix made the model worse.
- **Writing a second name.** On 360 test items where the right next piece of a short Python line was a second variable name after an operator, the checkpoint that scored 164 of 200 never ranked the right opening byte at the top (0 of 360) and put a digit at the top 325 times (90.3 percent). On a control form needing one name, it ranked the right byte at the top 5 of 60 times and a digit 0 times. Varying the name's length, how far back it was defined and the digit width changed nothing. Limit: this is about this checkpoint and this kind of item. It is the weakness under the 11 of 25 family above, and the narrow mix above was my attempt to fix it.
- **Against Qwen2.5-Coder-0.5B.** On 256 fixed windows of 2,048 bytes of held-out code, it scored 0.788 bits per byte against 0.593 for Qwen2.5-Coder-0.5B, behind by 0.195, and won on 18 of the 256 windows. Larger Qwen models scored 0.496 at 1.5B and 0.442 at 7.6B. Limit: Qwen probably saw similar code, and the holdout is not proven clean.
- **My training log's best was too low.** My training log reported a best of 1.184 bits per byte. On 512 fixed, evenly spaced held-out windows of 1,024 bytes, the same saved model scored 1.3186 (95 percent interval 1.2842 to 1.3530), so I stopped quoting the training log's best. Limit: the log draws random windows and keeps the lowest of many noisy readings, so its best is low by construction. This measures my instrument. It does not say the model got worse.
- **Six tiny tasks.** On 1 Aug 2026 it wrote Python that ran and printed the right answer on 4 of 6 very small completion tasks within 24 tries each, and on 2 of 6 with the greedy try. After one pass over the 6.63 MB set it passed 6 of 6, and five more passes over the same set left the greedy count at 3 of 6, below the 4 of 6 I had registered. Limit: six tasks are too few to give a rate. The 200-task suite replaced this test the next day.
- **An earlier snapshot against Qwen2.5-Coder-7B.** At step 199,000 it lost to Qwen2.5-Coder-7B on general held-out text. That result has its own card: [Mark One 295M, step 199,000 snapshot](mark-one-220m-code.md).

My 40M model's 0 of 200 on real Python test files is a different model on a different test ([Mark One 40M](mark-one-40m-code.md)). The two are separate results, not a before and after.

## Where it falls short

- It is far under-trained: about 4 percent of its mix read at 200,000 steps.
- It did not beat any Qwen model it was compared with.
- It fails at writing a second variable name after an operator (0 of 360), and the data I built for that skill made it worse.
- My task suites are my own, the judge looks at printed output, and no other model was run on them.
